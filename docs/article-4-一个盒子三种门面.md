## 一、起因：出差背三个盒子

公司自己开发的上位机，有的只认 Vector，有的只认周立功，有的只认 PEAK。

于是出差要背三个盒子：一块 VN1630A、一块 USBCAN、一块 PCAN-USB。

**能不能只带一块，让它变成对方想要的样子？**

DLL 层转发就行 —— 上位机以为自己插的是某家的卡，实际底下是哪块盒子无所谓。

---

## 二、思路：一个内核，三套门面

```
        上位机（ZCANPRO / 厂家工具 / PEAK 系软件 / CANape）
                    │
        ┌───────────┼───────────┬──────────────┐
        │           │           │              │
   VCI_* 接口    ZCAN_* 接口   CAN_* 接口    xl* 接口
   USBCAN.dll    zlgcan.dll    PCANBasic.dll  （Vector 原生）
        │           │           │
        └───────────┴───────────┘
                    │
              中立帧模型 CtFrame
                    │
        ┌───────────┼───────────┬──────────┐
     Vector        PCAN        周立功      广成/创芯/同星
   vxlapi.dll   PCANBasic.dll  USBCAN_E.dll   ...
```

**关键点：门面（上位机看到的接口）和后端（实际用的硬件）是正交的。**

所以同一块 VN1630A，可以：

| 上位机认的接口 | 装的 DLL | 我们实测 |
|---|---|---|
| 周立功老 VCI（14 个导出） | `USBCAN.dll` | ZCANPRO 收 **141 帧**，0 错误 |
| 周立功新 VCI（61 个导出） | `zlgcan.dll` | 开设备 / 初始化 / 收发全通 |
| PEAK（16 个函数） | `PCANBasic.dll` | `CAN_Write` → `CAN_Read`，数据完整 |

**出差只带一块，不管对方软件认哪家。**

---

## 三、为什么选 Vector 当那块"唯一的盒子"

一开始我想用周立功当底，后来改了主意，三个原因：

1. **吞吐**：VN1630A 四路 CAN，实测每路 2000 帧/秒压测不丢
2. **时间戳**：硬件级，用它录的 ASC 比软件打点准得多
3. **它本来就是 Vector** —— CANape / CANoe 这类只认 Vector 的软件**原生就能用**，
   不用写假 `vxlapi.dll`

**换句话说：拿 Vector 当底，三面通吃；拿国产盒子当底，还得再写一层假 vxlapi。**

## 四、三个踩进去的坑（都有实测数字）

### 坑 1：把日志写在收发循环里，单次发送慢 57 倍

现象很诡异：设定 10ms 周期发送，实测 **12.5ms**；设定 1ms，实测 **3.1ms**。

```
设定 10ms  →  实测 12.50ms   多了 2.5ms
设定  1ms  →  实测  3.11ms   多了 2.1ms
设定 50ms  →  实测 52.76ms   多了 2.8ms
```

**多出来的时间是固定的 2ms 左右** —— 与周期无关，说明在发送路径里。

查下去，是我自己加的调试日志：

```c
// 日志函数（图省事，每写一条都开关文件）
FILE *f = _wfopen(path, L"ab");
fwrite(...);
fclose(f);

// 而发送路径每次发送写 3 条日志
LogF("Vector xlCanTransmit(%lu 帧) -> %lu", ...);
LogF("   参数: port=%lu mask=...", ...);
LogF("   ev[0]: tag=%u id=0x%lX ...", ...);
```

**3 次文件开关 ≈ 1.5~2ms**，和测量值完全吻合。

改成"前 5 次 + 每 1000 次记一条"之后：

```
VCI_Transmit 单次调用：1.877ms  →  0.033ms   （快 57 倍）
1ms 周期吞吐：1609 帧  →  2521 帧 / 5 秒
```

> **教训**：为了查问题加的日志，本身会变成问题。
> 往收发循环里加日志，从第一天就必须限流。

---

### 坑 2：错误帧被当成数据帧，发 19 帧收 9350 帧

调试另一个功能时发现：客户端只发了 **19 帧**，主进程收到 **9350 帧**。

把驱动返回的原始事件打出来：

```
原始事件: id=0x1AB  flags=0x1  dlc=8  data=00 ...
                          ↑ XL_CAN_MSG_FLAG_ERROR_FRAME
```

**发送得不到 ACK 时，Vector 会把每一次失败重试都报成一个"接收事件"**，
id / dlc / data 还都是原来那帧。

而我的接收循环只看 tag，不看 flags：

```c
if (tag != XL_RECEIVE_MSG) continue;   // 只判这个
```

于是错误帧被当成正常报文交给上位机。

**后果**：只要是"只发不收"的场景（台架上只有一个节点），
用户就会看到自己发的帧被"接收"几千次。

修法：`flags & XL_CAN_MSG_FLAG_ERROR_FRAME` 的丢掉并计数。
周立功的 `VCI_CAN_OBJ` 里没有"错误帧"这个类型，所以只能丢弃，
但至少要计数、要能查出来。

### 坑 3：时间戳每 4.29 秒往回跳

ZCANPRO 的时间标识列，数值会突然跳回小时候 —— 看起来像随机数。

两个错误叠在一起：

```c
// 错误 1：Vector 给的是 64 位【纳秒】，我取了低 32 位
o.TimeStamp = (DWORD)(nanoseconds & 0xFFFFFFFF);
// 2^32 纳秒 = 4.294967296 秒  ← 正好是观察到的回绕周期

// 错误 2：转换层又把它当【毫秒】用
ts_ns = TimeStamp * 1000000;
```

算下来等于"纳秒级的值再乘一百万"，还在 4.29 秒处翻回去。

统一成**0.1 毫秒**（周立功的老约定）之后：

```
Vector  纳秒 / 100000
PCAN    毫秒 * 10
VCI     微秒 / 100
Kvaser  毫秒 * 10
```

标定验证（每 1000ms 发一帧，记录墙上时间）：

| 墙上时间 | 报文时间戳 | 换算 |
|---|---|---|
| 1.003 s | 10029 | 10 单位/毫秒 |
| 2.007 s | 10040 | 10 单位/毫秒 |
| 4.016 s | 10049 | 10 单位/毫秒 |
| 5.020 s | 10040 | 10 单位/毫秒 |

**0.1 毫秒刻度、无回绕、漂移 < 0.05%。**

顺带把"永不为 0"做成了硬保证 —— ZCANPRO 遇到 `TimeFlag=0` 会显示
`0.000000`，列表里一格一个零，比差 0.1 毫秒糟糕得多。

## 五、多路并行：顺序错了就全错

ZCANPRO 按 USBCAN-II 打开两路，一开始第二路是**假的** ——
`InitCAN` 返回 1，但背后没有任何硬件动作。

Vector 支持一个 port 管多个通道（`xlOpenPort` 传组合 mask），
但**顺序错了必败**。我试了三次：

```
① 先开单路，再升级组合  → perm=0（自己占着一个通道，组合里含它）
② 关掉单路再开组合      → 只给了另一个，数量没变但接线那路没了
③ 想回退单路            → 驱动还没释放，整块设备打不开
```

原因是 Vector 的规矩：**同一个通道只有第一个打开它的应用拿到 init 权限**，
而且释放有延迟。

**正确做法：组合 mask 必须是第一个动作**，此时一个通道都没占：

```c
XLaccess perm = 0x3;                       // 申请 CAN1 + CAN2
xlOpenPort(&port, app, 0x3, &perm, 8192, 3, XL_BUS_TYPE_CAN);
// → perm = 0x3，一次拿到两路
```

然后每路各自设波特率、各自激活，接收按事件的 `chanIndex` 分流。

分流验证做了三步（这一步很关键，否则不知道自己有没有搞错）：

1. 两个 CAN 口接同一总线 → 同一帧两路各收一份
2. 在通道 1 发一帧 → 回显只落通道 1
3. 拔掉其中一根线 → 只有还接着那路有帧，另一路 0

## 六、两个程序同时用一块盒子

不用写常驻服务，也不用共享内存 —— **Vector 的授权是按通道算的**。

只要两个程序用**不同通道 + 不同应用名**：

```ini
# ZCANPRO 目录
xl_channel=1
app_name=ZCANPRO

# 另一个软件的目录
xl_channel=2
app_name=CANape
```

实测两个进程同时打开都拿到权限（`mask=0x1` 和 `mask=0x2`），
A 连续收到 B 发来的 78 帧，计数器 00→4D 连续。

> **注意**：两次打开必须用不同应用名。名字相同的话，Vector 当成同一个应用，
> 第二个拿不到 init 权限 —— 这个坑我踩了半天。

## 七、"不影响厂家软件"这条底线

这是整个项目最硬的要求：**装了桥，厂家自己的软件必须照常能用。**

### 问题

装桥之后，程序目录的 `USBCAN.dll` 变成了桥，而 ZCANPRO 是按名字加载的
（`kerneldlls\dll_cfg.ini` 里写着 `3=USBCAN.dll`），
所以桥**盖住了** `kerneldlls\USBCAN.dll` 那份原厂。

原来的原厂透传排在探测链**最后**：

```
PCAN → VCI×N → GCAN → TOSUN → KVASER → Vector → 原厂透传
```

前面任何一个后端"碰巧能打开"，真周立功盒子就轮不到 ——
用户看到的就是**"装了桥，我的周立功认不出来了"**。

### 修法

**在自动探测的最前面**，先把原厂 DLL 当后端试一次：

```
候选 1  <目录>\<自己的文件名>.zlg.bak
候选 2  <目录>\USBCAN.dll.zlg.bak
候选 3  <目录>\kerneldlls\USBCAN.dll      ← ZCANPRO 自带原厂
候选 4  <目录>\kerneldlls\USBCAN.dll.zlg.bak

每个都必须：不是桥自己（身份证检查）+ 真的能 OpenDevice 成功
```

**为什么这个顺序是对的**：插的是真周立功盒子时，桥能提供的价值是零
（本来就是同一块硬件），原厂 DLL 最稳、功能最全。插别家盒子时原厂打不开，
自然往下走。

## 八、顺带踩到的一个"老驱动"陷阱

老款周立功 USBCAN-II 在 Win11 25H2 上装不上，设备管理器一个黄色感叹号。

一路查下来：

```
设备问题代码 : 39
手动启动服务 : sc start ZLGCAN → 错误 193
问题状态     : 0xC000007B (STATUS_INVALID_IMAGE_FORMAT)
```

读 PE 头：

```
usbcan.sys      (2017)  MajorSubsystemVersion = 1.10   ← 非法
USBCAN_E_U.sys  (2020)  MajorSubsystemVersion = 6.1    ← 正常
```

**Windows 10/11 的内核加载器要求驱动子系统版本 ≥ 6.0**，
1.10 是 XP 时代的值，直接被拒。

**两个容易走的弯路（我都差点走）：**

- ❌ **关内存完整性**：同一台机器、HVCI 全程开着，2020 年那版驱动正常 RUNNING。
  说明不是 HVCI 拦的，关掉白关。
- ❌ **重装驱动**：跑了官方安装包（退出码 0），`usbcan.sys` 的 SHA256 一字节没变，
  还是同一个 2017 文件。安装包和已装的是同一版。

**结论**：老盒子在这类新系统上没救，换新款（2020 驱动）或者换机器。

## 十、还缺什么（诚实列表）

- **CAN FD 没接**。数据结构支持 64 字节载荷，但没有任何厂商的 FD 路径接上。
  这是目前最大的缺口。
- **同星 / 广成 / Kvaser 没在真机验证** —— 代码写了，没硬件。
- **同一条通道跨进程共享**（两个程序抢同一路 CAN）只有实验性原型：
  客户端能接入、能收广播帧，但通过共享路径发出的帧在测试接线下拿不到 ACK，
  根因还没定位。**可靠的做法是按通道分离，不是共享同一路。**
- **CANape 用国产盒子（假 vxlapi）还没做通**，目前只有个记录调用的空壳。

## 十二、几条通用经验（不用这个工具也能用）

1. **"只发不收"的场景要小心错误帧**。CAN 没有 ACK 就不会完成传输，
   有些驱动会把它报成接收事件，看起来像收到了一堆数据。
2. **时间戳单位一定要标定**。别信文档，用"每 1000ms 发一帧、看差值"实测。
3. **热路径里不要有文件 I/O**。一条日志的代价可能是几百微秒。
4. **驱动加载失败先读 PE 头**。`MajorSubsystemVersion < 6.0` 在新系统上一定失败，
   跟签名、跟内存完整性都没关系。
5. **"通道数没变"不等于"没变差"**。重新打开时从 CAN1 换到 CAN2，
   数量一样但功能没了。
