手上的情况是这样的：

一块周立功 USBCAN-2E-U，一块创芯 CANalyst-II，平时用 ZCANPRO 看报文，
一切正常。

但要做标定，得用 CANape。而 CANape 的设备列表里只有 Vector 那几款 ——
VN1610、VN1630、VN1640。插着周立功的盒子，它看不见。

买一块 VN1630？两万多。

于是我花了两天，写了个 DLL 转发层：让 CANape 以为插的是 VN1630，
实际把每一帧转发给那块两千块的周立功盒子。


--------------------------------------------------
  一、为什么软件会"只认某个牌子"
--------------------------------------------------

这不是软件故意排外，是 Windows 的加载机制决定的。

上位机要跟 CAN 盒子通信，必须加载厂家提供的 DLL：

    ZCANPRO   →  zlgcan.dll / USBCAN.dll
    CANape    →  vxlapi.dll   (Vector XL API)
    PCAN-View →  PCANBasic.dll

Windows 找 DLL 的顺序是：

    ① 程序自己的目录
    ② 系统目录 System32 / SysWOW64
    ③ PATH

所以只要我们在①的位置放一个**同名但内容是自己的** DLL，
上位机就会加载它 —— 而它以为自己拿到的是原厂的。

这就是"门面"（shim）。原理极简单，难的是**把这个门面做得足够真**。


--------------------------------------------------
  二、坑一：一个结构体，16 字节还是 18 字节
--------------------------------------------------

周立功的 VCI 接口里有个初始化结构体 VCI_INIT_CONFIG。

我一开始"记得"是 18 字节，写成了：

    typedef struct {
        BYTE  Mode;
        BYTE  InitBytes;
        DWORD AccCode;
        DWORD AccMask;
        DWORD Reserved;
        BYTE  Filter;
        BYTE  Timing0;
        BYTE  Timing1;
        BYTE  Mode2;
    } VCI_INIT_CONFIG;

官方其实是 **16 字节**，前面没有 Mode/InitBytes：

    typedef struct _INIT_CONFIG {
        DWORD AccCode;
        DWORD AccMask;
        DWORD Reserved;
        UCHAR Filter;
        UCHAR Timing0;
        UCHAR Timing1;
        UCHAR Mode;
    } VCI_INIT_CONFIG;

后果不是崩溃，而是**所有字段错位 2 字节**。

日志里打出来的是：

    Filter=28  Timing0=0x00  Timing1=0x88  Mode2=121

我盯着这堆数字排查了很久，还据此得出"布局肯定不一样"的结论 ——
**而 Mode2=121 其实是越过结构体末尾的栈垃圾。**

那天我因为这个错误判断，把方向带偏了两次。

后来加了一行编译期断言，这类问题就再也不会发生了：

    typedef char CHECK[(sizeof(VCI_INIT_CONFIG) == 16) ? 1 : -1];

一行断言抓出的问题，比两天的日志分析还多。


--------------------------------------------------
  三、坑二：36MHz 和 16MHz
--------------------------------------------------

接下来是更隐蔽的一个。

周立功的 USBCAN-II（老款）和 USBCAN-2E-U（新款）**用同一套接口函数**，
所以看起来只要改个型号就能用。但它们的 CAN 控制器时钟不一样：

    老款 USBCAN-II  →  16 MHz
    新款 2E-U       →  **36 MHz**

我照着 16MHz 算出波特率时序字节（Timing0/Timing1），填进去。

结果是：**能打开、能启动、一帧收不到，同时错误帧刷了 74458 条。**

错误帧这个细节很关键 —— 它说明总线有信号，只是采样点对不上。
如果连错误帧都没有，那是没接总线（或者 CAN_H/CAN_L 接反了）。

翻官方手册才发现一句关键的话：

    USBCAN-E/2E-U 的 CAN 控制器使用 36MHz 时钟

以及更重要的一句：

    波特率必须通过 VCI_SetReference 设置，
    VCI_InitCAN 里的 Timing0/Timing1 被硬化忽略

也就是说 —— **对新款盒子，时序字节根本没人看**。
波特率要靠另一个函数下发，而且必须**在 InitCAN 之前**：

    DWORD baud = 0x060007;                    // 500K
    VCI_SetReference(21, 0, ch, 0, &baud);    // 先设波特率
    VCI_InitCAN(21, 0, ch, &cfg);             // 再初始化

改完，一帧变 4650 帧。

顺带记一下官方的波特率参考码（手册第 36 页，这些不能靠公式推）：

    0x060003  1000K     0x060004  800K      0x060007  500K
    0x1C0008  250K      0x1C0011  125K      0x160023  100K
    0x1C002C  50K       0x1600B3  20K       0x1C00E0  10K
    0x1C01C1  5K

我一开始试着按位域反推，算出来 2666667 bps —— 明显是位域假设错了。
**这种表只能抄，不能推。**


--------------------------------------------------
  四、坑三：关设备用错型号，会把驱动卡死
--------------------------------------------------

这个坑最恶劣，因为**它会让厂家的软件也用不了**。

我写的转发层里有个全局变量记着"打开的型号"，初值是 3。
探测阶段用型号 21 打开了 2E-U，但关设备时用的是这个初值：

    CloseDevice(3, 0);     // 错的，应该是 21

型号不对，驱动返回失败 —— **设备根本没关掉**。

驱动里于是留着一条"设备已被占用"的记录，而占用它的进程已经退出了。
之后：

    · 原厂 ZCANPRO 打不开
    · 我自己的工具也打不开
    · 拔插盒子没用
    · **重装 ZCANPRO 就好使，甚至不用重启电脑**

最后这一条是破案的关键。

"不用重启"意味着问题在**用户态/文件层**，不是内核驱动。
这一下把排查范围缩小了一大半。

顺着这个线索去看卸载逻辑，又发现第二个更严重的问题：

    卸载时如果没有原厂备份，
    代码会因为"文件大小和我的 DLL 一样"就直接删掉 USBCAN.dll

删掉之后，上位机目录里没有设备插件了 ——
表现就是"卸载之后反而更坏"，而且**重装软件立刻恢复**。

现在的做法：

    · 关闭设备用【实际打开的型号】，无条件执行，并打印返回值
    · 卸载时先找 kerneldlls 里的原厂副本还原；都没有才删，且给出警告
    · 备份前先判断：要备份的这个文件是不是桥自己


--------------------------------------------------
  五、怎么做到"不弄坏厂家的软件"
--------------------------------------------------

这一点比功能重要。因为使用者可能同时装着 CANoe、CANape、ZCANPRO，
不能因为我们的工具让它们坏掉。

三道保险：

**【一】优先用 App.exe.local 重定向，不改程序目录**

Windows 有个机制：如果程序目录下存在 <程序名>.exe.local 文件夹，
加载器会优先搜这个文件夹。

    CANape 安装目录\
    ├── CANape.exe          ← 不动
    ├── vxlapi.dll          ← 不动（原厂的）
    └── CANape.exe.local\   ← 只新增这个文件夹
            vxlapi.dll      ← 我们的

**卸载 = 删掉那个文件夹。** 现有文件一个字节都没改。

**【二】必须改文件时，先备份，且备份要可用**

备份文件名固定后缀，卸载工具据此还原。
没有验证过还原路径，绝不删除厂家文件。

**【三】独立的"一键恢复"工具**

它不依赖主程序 —— 主程序坏了也能用。

    · 自动扫 ZCANPRO / CANape / CANoe 目录
    · 找 *.zlg.bak / *.canbridge.bak
    · 还原原文件，并把现场另存为 .replaced（误删也能找回）
    · 按 Y 之前不动任何文件


--------------------------------------------------
  六、现在能到什么程度（诚实版）
--------------------------------------------------

真机验证过的：

    周立功 USBCAN-2E-U   打开 ✓  设置波特率 ✓  发送 ✓  接收 4650 帧 ✓
    创芯 CANalyst        打开 ✓  设置波特率 ✓  发送 ✓  接收 2500 帧 ✓
    PEAK PCAN-USB        打开 ✓  设置波特率 ✓  发送 ✓

**还没做的、没验证的，也在仓库里写清楚了：**

    · 同星 / 广成 / Kvaser 后端代码写了，但没有硬件，未验证
    · CAN FD 和 LIN 的数据结构有了，通路还没接
    · Vector 自家盒子默认关闭（权限模型不同，会选错后端）

我最想避免的是"看起来能用，实际数据是错的"。
那种问题比"打不开"难查一百倍。

《验证记录与排查手册》—— 里面有一张表，用两个数字就能判断故障方向：

    接收帧数    错误帧数    结论
    ─────────────────────────────────────────────
    0           0           没接总线 / CAN_H、CAN_L 接反 / 插错通道
    0           万级        有信号但波特率或型号不对
    持续增长     0           正常
    少量        偶发        多半是终端电阻缺失

最后再多说一句：**结构体、寄存器、波特率码表这些东西，一定要照官方手册抄，
不要凭记忆，也不要用公式反推。** 我在这上面栽的两次，每次都值一天。
