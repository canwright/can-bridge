  一、这件事的本质
================================================

  Vector 的 CANoe / CANape 只认 Vector 硬件，因为：
    · 设备列表来自 Vector 内核驱动枚举出的【设备接口】
    · 这些接口只能由驱动创建，用户态程序造不出来

  但 Vector 驱动内置了一个【虚拟总线】，完全软件实现：
    · 不需要任何 USB 硬件
    · 上位机看到的是 "Virtual CAN Bus N"
    · 同一 Virtual CAN Bus 下的两条通道【互相配对】
      —— 一条上发的帧，另一条能收到

  所以：让 CANape 占一条虚拟通道，我们的中继占另一条，
       把中继那头接到真实硬件上，就形成了完整的桥。


  二、两条技术路线（业界都有人做）
================================================

  路线 A：虚拟通道桥接（本项目的做法，也是 SysMax 早期做法）
  ------------------------------------------------
     上位机 → Vector 虚拟通道 → 桥接软件 → 别的硬件驱动 → 真实盒子

     优点：
       · 不需要专用硬件，手边任何盒子都能用
       · 许可走原厂驱动，不受影响
       · 实现成本低（软件层）

     缺点（SysMax 官方文档里写明的，我们实测也一致）：
       · 时间戳经 Windows 软件转发，精度受系统调度影响
       · 无法提供 Vector 原生的错误帧显示
       · 无法提供 Vector 原生的总线负载率显示
       · 多一层转发，故障点更多，桥接软件必须一直运行

  路线 B：固件级原生驱动（SysMax 现在改走的路）
  ------------------------------------------------
     专用硬件（固件实现 Vector USB 协议）→ 原厂 Vector 驱动 → 上位机

     优点：
       · 上位机看到的设备名、时间戳、错误帧全是原生的
       · 真正的"无感"

     缺点：
       · 必须做硬件 + 内核驱动
       · 需要逆向 Vector 的私有 USB 协议
       · 需要驱动签名证书

  结论：
     应急、借用现有硬件 → 路线 A 够用
     要卖给客户、要体验一致 → 只能走路线 B


  三、虚拟通道的配对规则（实测确认）
================================================

  同一 "Virtual CAN Bus" 下的不同通道互相配对：

      通道 A（mask 0x20，chanIndex 5）
      通道 B（mask 0x40，chanIndex 6）

      A 发 → B 收    ✅ 实测 10/10
      B 发 → A 收    ✅ 实测 10/10

  要点：
    · 一个应用独占一条通道的【初始化权限】（init access）
    · 第二个应用打开同一条 → perm=0x0，收不到帧
    · 所以桥接软件和上位机必须占【不同的】通道
    · 通道数量由驱动配置决定，本机是 2 条


  四、踩过的坑（都是实测出来的）
================================================

  坑 1：xlReceive 的真实签名是 3 个参数
  ------------------------------------------------
      错误写法：xlReceive(port, &count, maxEvents, events)
      正确写法：xlReceive(port, &count, events)
                count 是"进=最多取多少，出=实际取到多少"

      违反后果：32 位 __stdcall 栈错乱 → 读到垃圾数据 →
                计数暴涨到几百万 → 崩溃

  坑 2：xlCanTransmit 发帧前没设 chanIndex
  ------------------------------------------------
      事件的 chanIndex 必须和端口所在通道一致，
      否则驱动访问错通道，直接访问违规。

  坑 3：应用名和通道绑定不一致
  ------------------------------------------------
      xlSetApplConfig("MyApp", ..., hwChannel) 会把应用绑到某一条通道，
      之后如果按 mask 打开另一条，驱动仍按应用的绑定投递 → 收不到。

      解决：要么不调 SetApplConfig，只按 mask 打开；
            要么保证绑定的通道和打开的 mask 是同一条。

  坑 4：接收队列一直空（XL_ERR_QUEUE_IS_EMPTY = 10）
  ------------------------------------------------
      SysMax 官方文档给的排查方向：
        "在 Vector Hardware Config 中，为对应虚拟通道手动添加应用，
         然后重新启动桥接服务。"
      对应报错 XL_ERR_WRONG_PARAMETER。

      我们最终没走通 C 版这条路，改用 python-can 才成功。

  坑 5：64 位进程加载不了 32 位的厂家 DLL
  ------------------------------------------------
      周立功只提供 32 位 USBCAN.dll。
      64 位的 CANape 侧必须通过【32 位辅助进程】中转：
        64 位门面 → 共享内存 → 32 位 helper → VCI → 盒子

  坑 6：桥接软件自己的发送会被驱动回环
  ------------------------------------------------
      往虚拟通道发出去的帧，驱动会回送给同一通道上的应用，
      如果桥接软件不区分"自己发的"和"别人发的"，
      就会无限自激（实测计数在 6 秒内涨到 580 万）。


  五、最终可用的实现（本项目）
================================================

  架构：
      CANape / CANoe（64位）
          ↓ Vector 虚拟通道（python-can 驱动）
      中继 VxlRelayPy.exe（Python，已打包成 exe）
          ↓ 共享内存环形队列
      VxlHelper.exe（32位，用 UniVciBridge 打开真硬件）
          ↓ VCI
      周立功盒子（USBCAN-II / 2E-U 等）
          ↓ 真实 CAN 总线
      ECU / 台架

  为什么两端分开：
      · Vector 侧用 python-can —— 它把这套 API 的坑都踩平了
      · 硬件侧用 32 位进程 —— 厂家 DLL 只有 32 位

  实测结果（2026-11-07）：
      虚拟通道 → 中继 → 周立功        发出 10 帧，全部送达
      VN1630A → 总线 → 周立功 → 中继 → 虚拟通道   收到 10/10

  已知限制：
      · 中继必须一直运行
      · 时间戳精度受系统调度影响
      · 无原生错误帧 / 负载率显示
      · Windows 的【内存完整性】必须关闭，否则老周立功驱动加载不了
