────────────────────────────────────────────────
  一、当前验证矩阵（真机实测）
────────────────────────────────────────────────

  盒子                     打开   设波特率    发送    接收
  ────────────────────────────────────────────────────────────
  周立功 USBCAN-2E-U        ✅     ✅(SetRef)  ⏳     ✅ 2473帧/0错误
  创芯 CANalyst             ✅     ✅(timing)  ✅     ✅ 已验证
  PEAK PCAN-USB             ✅     ✅(Baud)    ✅     ⏳ 需第二节点
  广成 GCAN                 ⚠ 无硬件，未验证
  周立功老款 USBCAN-II      ✗ 驱动在 Win11 24H2 加载不了（厂家问题）

  「设波特率」两条路径是关键区别：
    · 周立功 E-U 系列（型号 20/21/31/34）
        CAN 控制器 36MHz，必须用 VCI_SetReference 下发波特率，
        VCI_InitCAN 里的 Timing0/Timing1 被固件忽略。
    · 创芯 / 经典 USBCAN-II（型号 3/4）
        靠 VCI_InitCAN 里的 Timing0/Timing1 设波特率，
        不需要 SetReference。

    桥必须按设备型号走对应的路径，走错就收不到帧。


────────────────────────────────────────────────
  二、这次修掉的 9 个问题（都别再犯）
────────────────────────────────────────────────

  ① VCI_INIT_CONFIG 结构体必须 16 字节
     官方定义（周立功手册 P18 / 广成 ECanVci.h 双份一致）：
         DWORD AccCode; DWORD AccMask; DWORD Reserved;
         UCHAR Filter;  UCHAR Timing0; UCHAR Timing1; UCHAR Mode;
     之前写成 18 字节（前面多 Mode/InitBytes），导致读出来
     Filter/Timing/Mode 全部错位 2 字节 —— 排错时被这些假值
     误导过两次。

  ② 波特率参考码必须照官方表（周立功手册 P36）
     适用 USBCAN-E-U / 2E-U / PCI-5010-U / PCI-5020-U：
         0x060003 1000K   0x060004 800K    0x060007 500K
         0x1C0008 250K    0x1C0011 125K    0x160023 100K
         0x1C002C 50K     0x1600B3 20K     0x1C00E0 10K   0x1C01C1 5K
     必须在 VCI_InitCAN 之前调用 VCI_SetReference。

  ③ ZCANPRO 不会自己调 VCI_SetReference
     它按经典 USBCAN-II 只填 Timing 字节。
     所以对 E-U 系列，桥必须主动补一次 SetReference。

  ④ 型号必须对上硬件
     · 2E-U 是型号 21（双通道），不是 20（单通道 E-U）
     · 用 20 去开 2E-U，等于告诉驱动「这是单通道」，
       却去操作第 2 路 → 那个通道疯狂报错、一帧收不到
     · 探测顺序：优先用【上层请求的型号】，不匹配才退回候选表
       （创芯的 ControlCAN.dll 对 21 也返回成功，不优先用请求型号
         就会把创芯盒子当成 2E-U，走上 E-U 的 SetReference 路径）

  ⑤ 通道数规则（用户要求）
     1 个 CAN 口 → 暴露 1 路（当 USBCAN-I）
     ≥2 个 CAN 口 → 暴露 2 路（当 USBCAN-II）
     多余的 CAN 口 → 默认不使用（封顶 2）
     且不超过桥的上限 VCI_MAX_CHANNEL
     通道数从【设备型号】推，不信 BoardInfo
     （创芯/周立功的 BoardInfo.can_Num 都返回过 808470065 这种垃圾值）

  ⑥ 初始化配置原样转发，不要自作主张改
     周立功官方：「两个系列采用同一套接口函数库」。
     原厂路径能收，就是因为它传什么就用什么。

  ⑦ 探测失败要立即 VCI_CloseDevice
     拿错型号去 OpenDevice，即使返回失败，USB 端点和固件通道状态
     可能已被扰动，影响后续正确型号的打开。

  ⑧ 接收计数不能只信厂家库
     ZCANPRO 的流程是「先问 GetReceiveNum 有几帧，>0 才调 Receive」。
     桥自己维护接收缓冲，计数和取帧都由桥负责，两者必然一致。

  ⑨ 日志要能看清真相
     原始字节、按 16 字节布局解释、InitCAN 参数、收发帧数都要记。
     错位的假值曾把我带偏两次。

  三、诊断速查表（用两个数字就能判断方向）
────────────────────────────────────────────────

  接收帧数    错误帧数    结论
  ────────────────────────────────────────────────────────────
  0           0           ① 没接总线 / 接线断了
                          ② CAN_H、CAN_L 接反了
                             （反接时接收端永远看不到 dominant 位，
                               所以既收不到帧、也不会报错）
                          ③ 线插在另一个通道上

  0           大量(万级)  有信号但波特率不匹配
                          或者被当成单通道型号、却操作了第 2 路

  持续增长    0           正常 ✅

  少量        偶发        多半是终端电阻缺失（总线末端反射）
                          USBCAN-E/2E-U 内部没有 120Ω，
                          需要自己接在端子的 R+ / R- 之间


────────────────────────────────────────────────
  四、接线注意
────────────────────────────────────────────────

  · CAN_H 对 CAN_H、CAN_L 对 CAN_L、GND 对 GND
  · CAN_H / CAN_L 接反的典型表现：0 帧、0 错误帧（最难看出来的一种）
  · 总线两端各 120Ω。USBCAN-E/2E-U 卡内部没有内置终端电阻，
    需要接在接线端子的 R+ 和 R- 之间
  · 一个 CAN 设备只能被一个进程打开，测试前先把
    ZCANPRO / CANoe / APE 全部关掉，或者拔插一次盒子清固件状态

────────────────────────────────────────────────
  六、★★ 严重坑：不要用「选软件装桥」装 ZCANPRO ★★
────────────────────────────────────────────────

  事故经过（2026-11-04 16:00）：
    有人用「选软件装桥」选了 E:\ZCANPRO\ZCANPRO.exe
    工具判断它引用 zlgcan.dll、ZCAN_* 6 处
    → 把 zlgcan.dll 门面装进了 ZCANPRO 目录

  后果：
    把 ZCANPRO 自己的 zlgcan.dll 顶掉了。
    ZCANPRO 内部枚举设备走的就是 zlgcan.dll，
    门面报的型号/通道数跟原厂对不上，于是：

        MinGW Runtime Assertion
        devicemanager.cxx Line 731
        Expression: channelNumber_count(info.type)

    一打开「设备管理」就崩溃。
    而且卸载桥也没用 —— 因为坏的是 zlgcan.dll，不是 USBCAN.dll。

  判断依据：
    卸载桥之后，原厂 ZCANPRO + 2E-U 依然崩溃
    → 说明问题不在桥，而在 ZCANPRO 自己被动过的地方

  修复：
    重装 ZCANPRO（最干净）。
    或者手动：把 E:\ZCANPRO\zlgcan.dll.zlg.bak 改名回 zlgcan.dll

  ★ 正确做法：
      让 ZCANPRO 用别家盒子 → 只点「一键安装」
      它只装 USBCAN.dll，不碰 zlgcan.dll
      「选软件装桥」是给【别的软件】用的，不是给宿主 ZCANPRO 用的

  ★ 工具已加硬拦截：
      选到 ZCANPRO 会直接拒绝并说明原因

  ── 这一坑的普遍教训 ──
    桥有两种安装形态：
      ① 装成 USBCAN.dll  → 给 ZCANPRO / 其他用 VCI 的软件（安全）
      ② 装成 zlgcan.dll   → 给【直接调用 ZCAN API】的软件
    而 ZCANPRO 自己就用 zlgcan.dll，所以绝不能对它用 ②。


────────────────────────────────────────────────
  七、结构体布局的教训
────────────────────────────────────────────────

  一天之内因为「凭总大小判断结构体对不对」错了两次：

  ① VCI_INIT_CONFIG
     我以为 18 字节，官方是 16 字节。
     依据：周立功手册第 18 页 + 广成 ECanVci.h 双份一致
     后果：读出来的 Filter/Timing/Mode 全部错位 2 字节

  ② VCI_BOARD_INFO
     桥里写的是「4 个 DWORD + 20 + 40 + 4」，官方是：
         USHORT hw_Version;  USHORT fw_Version;
         USHORT dr_Version;  USHORT in_Version;
         USHORT irq_Num;     BYTE can_Num;      ← 偏移 10，1 个字节
         CHAR str_Serial_Num[20]; CHAR str_hw_Type[40]; USHORT Reserved[4];
     两者总大小都是 80 字节，但 can_Num 差了 2 个字节位置。
     后果：为了"修正"通道数而写 pInfo->can_Num，实际写到了序列号里，
           真正的 can_Num 被清 0 → ZCANPRO 的
           channelNumber_count(info.type) 对不上 → 断言崩溃。

  ★ 教训：
      结构体一定要照官方头文件逐字段核对，
      不能因为「总字节数一样」就认为布局一样。

────────────────────────────────────────────────
  八、★★ 句柄泄漏：关设备必须用「实际打开的型号」★★
────────────────────────────────────────────────

  这是今天最严重的一个 bug，症状最恶劣 ——
  桥自己看不出问题，但会让【厂家自己的软件用不了】。

  ── 症状 ──
    用完桥之后，把桥卸载掉，原厂 ZCANPRO 也打不开设备了。
    设备管理器里能看到盒子，驱动也没感叹号，但任何软件都打不开。
    ★ 只能重装 ZCANPRO（安装包会顺带重置 USB 驱动）或重启电脑。

  ── 根因 ──
    桥里有个全局 g_devType，初值是 3。
    探测成功时只更新了 g_vciRealType = ty（比如 21），
    退出释放时却用 g_devType 去关：

        g_vci.CloseDevice(g_devType, 0);     // CloseDevice(3, 0)，错的

    2E-U 是型号 21，拿 3 去关，驱动直接返回失败，
    设备根本没关掉 → 驱动里留着「设备已被占用」的记录，
    而占用它的进程已经退出 → 之后谁也打不开。

  ── 还有第二个漏洞 ──
    那句关闭代码原本包在
        else if (g_backend == BE_GCAN || g_backend == BE_VCI)
    里面。如果探测阶段打开了设备、但后端最终没被选定
    （g_backend 变回 BE_NONE），这个分支就进不去 → 同样泄漏。

  ── 修法 ──
    ① 用真正打开成功的型号去关：
           DWORD closeType = g_vciRealType ? g_vciRealType : g_devType;
           g_vci.CloseDevice(closeType, 0);
    ② 探测成功时同步记下型号：g_devType = ty;
    ③ 关闭逻辑移出 else-if 链，改成【只看 g_vciOpened】，无条件执行
    ④ 打印返回值，便于确认：
           退出兜底关闭 VCI 设备：CloseDevice(21) -> 1

  ── 验证结果（2026-11-04 16:50）──
    ★ 卸载桥之后，原厂 ZCANPRO 直接就能用，不需要重装 ZCANPRO。
    → 句柄泄漏已彻底修复，「不影响厂家软件」这条底线守住了。

  ── 普遍教训 ──
    打开和关闭必须【严格配对】：
      · 用同一个型号
      · 无条件执行，不能看后端状态
      · 打印返回值，否则永远不知道有没有关成功

    探测阶段的任何"主动动作"（关设备、改状态）都很危险 ——
    探测只能"看"，不能"动"。


────────────────────────────────────────────────
  九、今天的 bug 分类总结
────────────────────────────────────────────────

  全部集中在【探测 / 关闭阶段】，协议转换本身一次没错：

  ① VCI_INIT_CONFIG 结构体 18 字节 → 官方 16 字节
  ② VCI_BOARD_INFO 字段错位 → 官方布局（can_Num 偏移 10，1 字节）
  ③ 探测优先用请求型号 → 改成按 DLL 家族（否则 E-U 被当成型号 4）
  ④ 探测失败就 CloseDevice → 删掉（会把已插好的设备关掉，越探越坏）
  ⑤ 关设备时不看后端类型 → 改成无条件执行
  ⑥ 关设备时用错型号 → 改成用 g_vciRealType
  ⑦ 选软件装桥装进 ZCANPRO → 硬拦截（四个判据）

  规律：打开/关闭/探测这三件事，任何一处不严谨都会
        表现为"设备打不开"，而且极难定位。

────────────────────────────────────────────────
  十、不改程序文件也能换 DLL：App.exe.local
────────────────────────────────────────────────

  需求：给某个软件塞一个假的 vxlapi.dll / USBCAN.dll，
        但【不想动它安装目录里的任何现有文件】。

  原理（Win11 实测有效）：
    Windows 加载 DLL 时，如果程序目录下存在文件夹
        <程序名>.exe.local
    会先搜这个文件夹，再搜程序目录。

    所以只需要在程序目录里【新建一个文件夹】，把我们的 DLL 放进去。
    程序本身、原厂的 DLL、System32 全都不用动。

  实测记录（2026-11-05，Win11）：
    目录：
        DotLocalTest.exe
        probe_tag.dll                （标记 APPDIR）
        DotLocalTest.exe.local\
            probe_tag.dll            （标记 LOCALDIR）
    结果：
        LoadLibrary("probe_tag.dll") 加载到
            ...\DotLocalTest.exe.Local\probe_tag.dll
        即 .local 生效。

  用法（以 CANape 为例）：
        CANape 安装目录\
        ├── CANape.exe          ← 不动
        ├── vxlapi.dll          ← 不动
        └── CANape.exe.local\   ← 只新增这个文件夹
                vxlapi.dll      ← 我们的

    卸载 = 删掉那个文件夹。

  限制（必须知道）：
    · 只对【按名字】LoadLibrary("xxx.dll") 生效；
      如果软件是按完整路径加载，.local 不起作用。
    · 万一不生效，最坏结果是"我们的 DLL 没被加载"，不会弄坏软件。

  和「一键恢复」的关系：
    .local 方式没有覆盖任何文件，所以不需要还原；
    但如果用了改名备份的方式（xxx.dll.canbridge.bak），一键恢复负责还原。
