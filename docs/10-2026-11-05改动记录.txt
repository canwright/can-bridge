────────────────────────────────────────────────
  二、三个"查了很久"的 bug
────────────────────────────────────────────────

  【bug 1】xlOpenPort 的 permissionMask 是 in/out

     现象：32 次尝试 perm 全 0，status 却是 0（成功）。

     真因：这个参数既是"我要申请哪些通道"，也是"实际给了你哪些"。
           手册示例第一行就写着要先赋值：

               xlPermissionMask = m_xlChannelMask;
               xlOpenPort(..., &xlPermissionMask, ...);

           我们一直传 0，等于一个通道都不申请。驱动就老老实实
           返回 perm=0，而 status 仍然是 0。

     教训：in/out 参数传 0 不会报错，只会静默地"什么都不给"。
           这类 bug 光看返回码永远查不出来，必须对照手册示例。


  【bug 2】xlCanTransmit 要 XLevent，不是裸 XLcanMsg

     现象：返回 101（XL_ERR_WRONG_PARAMETER）。

     真因：手册 5.5.1 的示例写得很清楚，传的是事件数组，
           tag 要设成 XL_TRANSMIT_MSG，报文放在 tagData.msg 里：

               XLevent xlEvent[100];
               memset(xlEvent, 0, sizeof(xlEvent));
               xlEvent[i].tag            = XL_TRANSMIT_MSG;
               xlEvent[i].tagData.msg.id = 0x04;

           我们直接传 XLcanMsg，驱动把 msg.id 当成 tag 读，认不出来。

     备注：桥里早就为接收定义了 48 字节的 XLevent，只是发送没用它。


  【bug 3】busStatus 是位掩码，不是枚举

     现象：日志里 busStatus=8、4、2 全显示成 "?"。

     真因：按 0/1/2/3 解码了，而实际是位掩码：

           0x01 BUSOFF        0x02 错误被动
           0x04 错误警告       0x08 错误主动（正常态）

     改完之后立刻读出了真问题：TEC=0、REC 涨到 128。


────────────────────────────────────────────────
  三、时间戳：两个错误叠在一起
────────────────────────────────────────────────

  现象：ZCANPRO 里时间标识每隔几秒往回跳，像垃圾数据。

  两个错误：

    ① Vector 的 timeStamp 是 64 位【纳秒】，我们取低 32 位 ——
       每 4.294967296 秒回绕一次。

    ② 转换层又把它当【毫秒】用（* 1000000），
       等于纳米级的值再乘一百万。

  统一后的约定：VCI_CAN_OBJ.TimeStamp 单位 = 0.1 毫秒（ZLG 老约定）

       Vector  纳秒 / 100000
       PCAN    毫秒 * 10
       VCI     微秒 / 100
       Kvaser  毫秒 * 10

  另外：出口处保证【永不为 0】且单调 —— 算出 0 就用上一个值 +1。
        ZCANPRO 遇到 TimeFlag=0 会显示 0.000000，列表里一格一个零，
        比差 0.1 毫秒糟糕得多。

  标定验证（每 1000ms 发一帧，记录墙上时间）：

       1.003 s → 10029 单位
       2.007 s → 10040 单位
       4.016 s → 10049 单位
       5.020 s → 10040 单位

       10 单位/毫秒、无回绕、漂移 < 0.05%。


────────────────────────────────────────────────
  四、性能：热路径上不能有文件 I/O
────────────────────────────────────────────────

  现象：周期发送设定 10ms，实测 12.5ms；设定 1ms，实测 3.1ms。

  真因：Vector 发送路径每次发送写 3 条日志，而 LogLine 每写一条
        都是 _wfopen + fwrite + fclose —— 一次文件开关几百微秒。
        3 次就是 1.5~2 毫秒。

  这些日志是查 101 错误时加的，忘了收。

  改成前 5 次 + 每 1000 次记一条之后：

       VCI_Transmit 单次:  1.877 ms → 0.033 ms   （快 57 倍）
       10ms 周期实测:      12.50 ms → 10.61 ms
       1ms 周期吞吐:       1609 帧 → 2521 帧 / 5 秒

  教训：往收发循环里加日志，从第一天就必须限流。
        为了查问题加的日志，本身会变成问题。


────────────────────────────────────────────────
  五、多路并行：顺序是成败关键
────────────────────────────────────────────────

  ZCANPRO 按 USBCAN-II 打开 2 路，以前第二路是假的 ——
  InitCAN 返回 1，但背后没有任何硬件动作。

  Vector 支持一个 port 管多个通道（xlOpenPort 传组合 mask），
  但顺序错了就失败。三次尝试：

      先开单路，再升级组合   → perm=0（自己占着一个通道）
      关掉单路再开组合       → 只给了另一个，数量没变但口换了
      想回退单路             → 驱动还没释放，整块设备打不开

  正确做法：**组合 mask 必须是第一个动作**，此时一个通道都没占：

      xlOpenPort(mask=0x3) → perm=0x3

  然后每路各自 xlCanSetChannelBitrate / xlActivateChannel，
  接收按事件的 chanIndex 分流到各路缓冲。

  分流验证做了三步：

      两个 CAN 口接同一总线 → 同一帧两路各收一份
      在通道 1 发一帧       → 回显只落通道 1
      拔掉其中一根线         → 只有还接着那路有帧，另一路 0


────────────────────────────────────────────────
  六、错误帧冒充数据帧（影响所有场景）
────────────────────────────────────────────────

  现象：调试跨进程共享时，客户端发 19 帧，Owner 收到 9350 帧。

  真因：发送得不到 ACK 时，Vector 把【每一次失败重试】都报成一个
        带 ERROR_FRAME 标志的接收事件，id/dlc/data 还都是原来那帧：

            原始事件: id=0x1AB flags=0x1 dlc=8
                                 ↑ XL_CAN_MSG_FLAG_ERROR_FRAME

        我们只看 tag 不看 flags，于是错误帧被当成正常报文交上去。

  后果：只要是"只发不收"的场景（台架上只有一个节点），
        用户会看到自己发的帧被"接收"几千次。

  VCI_CAN_OBJ 没有错误帧这个类型，所以只能丢弃 + 计数，
  日志里报累计值（限流，不会刷屏）。


────────────────────────────────────────────────
  七、错误状态回传
────────────────────────────────────────────────

  以前 VCI_ReadErrInfo 对 Vector 直接清零 —— 总线关闭了，
  上位机还显示"一切正常"，唯一症状是"收不到帧"。

  三处必须一起改：

    ① 芯片状态原来是全局一份，两路会互相覆盖 → 改成按通道
    ② 只发不收的上位机永远不调 Receive → 泵不跑 → 状态永远是 0
       所以 ReadErrInfo 里要先泵一次
    ③ 手册 5.5.2 明说事件要在 xlCanRequestChipState() 之后产生，
       桥根本没加载这个函数 → 主动索取

  实测：无应答连发 40 帧 → ErrCode=2（错误被动）、REC=128。


────────────────────────────────────────────────
  八、验收滤波
────────────────────────────────────────────────

  以前上层设了滤波，桥全收再全给 —— 高负载时白白拖慢上位机，
  而且不报错。

  ZLG 语义：AccMask 的位 = 1 表示"不关心"，= 0 表示参与比较

      接受条件：(id & ~mask) == (code & ~mask)

  代入 ZCANPRO 的默认值 AccMask=0xFFFFFFFF：~mask = 0，
  0 == 0 恒成立 → 全收，**和以前行为完全一致**。

  只有真的设了滤波的软件才会看到区别 —— 而那正是它期望的。

  实测：mask=0xFFFFFFFF → 0x100/0x110/0x120 全进；
        mask=0x1FFFF800 → 只有 0x100 进，另两个被挡掉。


────────────────────────────────────────────────
  九、真周立功优先（"不影响厂家软件"的底线）
────────────────────────────────────────────────

  问题：装桥后，程序目录的 USBCAN.dll 就是桥，它盖住了
        kerneldlls\USBCAN.dll（原厂那份）。

        而原厂透传排在探测链最后：
            PCAN → VCI×N → GCAN → TOSUN → KVASER → Vector → 透传

        前面任何一个后端碰巧能打开，真周立功盒子就轮不到 ——
        用户看到的就是"开启桥后周立功设备无法识别"。

  做法：在自动探测的【最前面】先把原厂 DLL 当后端试一次，
        能打开设备就立刻用它，后面的探测全跳过。

        候选：
            <目录>\<自己的文件名>.zlg.bak
            <目录>\USBCAN.dll.zlg.bak
            <目录>\kerneldlls\USBCAN.dll
            <目录>\kerneldlls\USBCAN.dll.zlg.bak
            <目录>\kerneldlls\usbcan.dll

        每个都要：不是桥自己（身份证检查 UniVciBridgeIdent）
                 + 真的能 OpenDevice 成功。

  为什么这个顺序是对的：插的是真周立功盒子时，桥能提供的价值是零
  （本来就是同一块硬件），用原厂 DLL 最稳、功能最全、厂家软件
  行为完全一致。插别家盒子时原厂打不开，自然往下走。


────────────────────────────────────────────────
  十、多软件共用一块盒子（不需要常驻服务）
────────────────────────────────────────────────

  Vector 的 init 权限是【按通道】算的，所以两个程序只要用不同通道
  就能同时用一块盒子。缺的只是"应用名" —— 两边都叫 UniVciBridge 时
  Vector 当成同一个应用，第二个拿不到权限。

  加了 ini 的 app_name 之后实测：

      A: xl_channel=1  app_name=ZCANPRO  → mask=0x1 (CAN1)
      B: xl_channel=2  app_name=CANape   → mask=0x2 (CAN2)

      A 连续收到 B 发来的 78 帧，计数器 00→4D 连续。

  同一通道共享（共享内存 IPC）做了原型：客户端接入、帧路由都通了，
  但通过共享路径发出的帧拿不到 ACK，没定位到根因。
  **默认关闭（要 ini 写 share=1），标记为实验性。**

────────────────────────────────────────────────
  十二、当天踩到的三个"测试工具"自己的 bug
────────────────────────────────────────────────

  同一个坑踩了三次，值得记：

  ① 特殊模式在 ch 解析之前就用 ch
     → 请求"通道 2147483653"，桥返回 113（XL_ERR_INVALID_CHANNEL）
     → 修法：ch 的解析提到所有模式之前

  ② printf 参数求值顺序未定义
     → printf("...", InitCAN(...), StartCAN(...))
     → 编译器可能先调 StartCAN，打印出 "StartCAN -> 0"，
       看起来像桥的 bug，其实是测试代码的错
     → 修法：分开调用，各存一个变量

  ③ 用 Start-Job 起后台浸泡
     → pwsh 进程一退出，子 job 就被杀，5 分钟测试 40 秒就没了
     → 修法：用 Start-Process，或 managed background job
